# 审批工作流的有限评估

选择一个应用：发布须先审批，撤销审批应阻止后续发布，同时已审批发布应可完成。范围为 pending/approved/released 三个状态、noop/approve/revoke/release 四个动作、三个固定路径、三个候选和八行响应宇宙。三个路径以外的循环、并发、跨实例和人员权限不在此次主张内。

当前没有提供实际业务记录与参与者数据。`examples/approval_workflow.py` 使用独立规定的观测夹具来完成工程验证；这是一份可替换数据的应用评估，不构成真实部署或用户试用结论。建模时间、人工复核成本与反例理解度保留 null，不能用构造耗时替代。

```bash
PYTHONPATH=src python examples/approval_workflow.py --output-dir /tmp/approval
```

| 阶段 | 可检查的结果 |
| --- | --- |
| 声明目的、生成候选 | guarded 要求审批并尊重撤销；shortcut 无审批即可发布；sticky 忽略撤销。没有证据时三个候选都相容，答案歧义 |
| 采集证据 | 独立夹具规定 release → pending，approve/release → released，approve/revoke/release → pending。预测不能用作这三条观测 |
| 排除 | 只剩 guarded；shortcut 与 sticky 各有一个活跃经验冲突，说明图经过复核 |
| 撤回 | 撤回第三条记录使忽略撤销的冲突失效，sticky 重返相容集合；无审批发布仍被首条记录排除 |
| 重新验证 | 第三条记录以新来源替换，重新建立冲突并只保留 guarded；完整有限表归档在新进程重放 |

报告记录每阶段的操作数、程序耗时、双轮采集次数、活跃/撤销证书、未决列表和原因。反例用“动作路径—预测状态—实际状态”呈现，例如 sticky 的 approve/revoke/release 预测 released、记录 pending。读者不必解释指纹才能指出哪个转移规则出错，但是否真正理解仍须参与者验证。
